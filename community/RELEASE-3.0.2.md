# RTX 3070 macOS 26 社区实验版 3.0.2

分享一个基于 **NullMoth NVIDIA macOS Driver v3.0** 的第三方整合包。我们在一张 RTX 3070 8 GiB 上追踪拖动大窗口和切换应用时的卡顿，找到一个可以稳定复现的问题：5K 窗口连续申请三块画面缓冲区时，旧版经常只备好一块，剩下两块要现场分配。本次改动让驱动提前准备这些缓冲区。同机预热后的 12 次申请中，命中数从 **4 次提高到 12 次**，分配耗时中位数从 **159.1 ms 降至 8.7 ms**。[上游项目与 v3.0 发行版](https://github.com/nullmoth/nvidia-macos-driver/releases/tag/v3.0)

## 适用环境

| 项目 | 要求或实测情况 |
|---|---|
| 显卡 | GeForce RTX 3070，安装器检查 PCI ID `10de:2488` |
| 平台 | x86_64 macOS 26，实测为 26.6.2（25G83） |
| 安装前提 | 已安装 NullMoth 3.0，且原驱动所需的固件已就绪。新驱动重启后加载 |
| 测试显示模式 | 5120 × 2880 渲染、2560 × 1440 逻辑分辨率、160 Hz |

## 这个包改了什么

1. **大窗口显存分配。** NVRMFB 在显存映射窗口（BAR1）足够大时，为最近使用的两种画面尺寸预先分配并清零缓冲区。测试中的两种尺寸各可保留三块。预备池最多六块、合计上限 448 MiB，并为正常显示分配保留余量。切回刚用过的窗口尺寸时，也有机会直接复用。
2. **桌面合成与画面同步。** WindowServer 可以复用同一 IOSurface 已导入的显存和主机内存页。符合条件的小纹理使用独立快照异步上传。驱动跟踪表面的写入状态，把 GPU 完成通知与屏幕捕获时的锁竞争隔开，让翻页和捕获都能判断相关写入何时完成。显存占用超过整卡容量的 80% 时，导入缓存可优先释放空闲项。
3. **Metal 提交队列与资源释放。** 调整提前安排的命令提交顺序，确保同一队列的工作按序执行。一段命令提交失败时，后续分段会停在失败点；驱动先记录错误，再唤醒等待线程。专项实测中，8 个线程共用一条 Metal 队列，完成 1,024 次提交，输出逐字节一致。对满足条件的大纹理和已导入内存，在 GPU 完成后延迟回收，减少渲染线程同步释放资源时的等待。
4. **GPU 传输与纹理采样器。** 对起点或尾部没有按内存页对齐的窗口图像，中间完整页可直接导入 GPU，只对边缘数据使用暂存区。在开发阶段的 236 次上传测试中，有 152 次采用了这条路径，像素与边界保护区均通过校验。另一个专项测试连续创建 8,192 个非归一化坐标 Metal 纹理采样器，耗时从约 149 ms 降至约 12 ms。
5. **着色器。** NVK 通过 GPU 上传队列把着色器代码放入显存。Metal 插件还能在 WindowServer 加载着色器库时，后台预热此前用过的函数常量组合，并复用正在进行的翻译，减少首次使用同一变体时的重复工作。
6. **视频解码。** GA104 上符合布局条件的 AV1、VP9 解码帧可通过 GPU 拷贝引擎保留在显存，再交给 VideoToolbox。AV1 8 位、AV1 10 位和 VP9 三组样片的亮度、色度平面校验值均与预期一致。其他布局仍可走原有回读路径。
7. **显示输出。** 当主显示平面报告支持时，驱动可从显存直接扫描输出打包的 10 位 `l10r` 表面，并用主平面颜色转换处理通道顺序。本次 5K / 160 Hz 实测没有触发该路径，10 位输出和 HDR 仍需另行验证。
8. **安装选项。** 一个 PKG 整合了实测驱动组合。默认只选择驱动。「全局 Metal 偏好」用于请求支持 ANGLE 的应用使用 Metal；「启用 GPU Boost」用于启用驱动现有的性能状态请求。两项可以独立勾选。

**配套性能查看器 1.8** 的源码位于 ZIP 的 `companion/performance-viewer/`。录制 CSV 时约每 100 ms 读取一次 GPU 利用率，这张 RTX 3070 的固件实测约每 250 ms 发布一笔新数据。日志保留固件时间戳，可以区分新数据与重复读数，也能查到一次翻页停顿结束前最近的 GPU 样本。

## 5K 桌面实测

下表对比的是**同一台机器升级显存预备池前后的两个本地版本**。缓冲区测试交替使用两种尺寸，共四轮，每轮申请三块。前后各跑一轮 8 秒拖窗和 20 次应用切换。P95 表示 95% 的观测值不超过该耗时。

| 指标 | 先前本地版本 | 本地 3.0.2 |
|---|---:|---:|
| 预热后 12 次大缓冲区申请命中 | 4/12 | **12/12** |
| 缓冲区分配耗时中位数 | 159.1 ms | **8.7 ms** |
| 三轮可见 5K 窗口中，超过 100 ms 的翻页间隔 | 7 次 | **1 次** |
| 拖动标题栏时的翻页间隔 P95 | 21.0 ms | **16.0 ms** |
| 切换应用后，系统确认前台应用的耗时 P95 | 57.6 ms | **29.0 ms** |
| 切换请求到首次全局翻页的耗时 P95 | 32.1 ms | **40.4 ms** |

首次遇到尚未预备的尺寸时，仍测到一次 **225 ms** 的分配。在三块预备缓冲区全部命中的一轮里，也记录到一次至少 **141 ms** 的翻页停顿。由此能确认大缓冲区分配得到改善，其他桌面停顿仍需定位。原始使用日志中约 800 ms 的卡顿在复测中没有重现。

另以同一套本机内核和 Vulkan 库，直接对测了**官方 v3.0 与本地 Metal 插件**。两个 Metal 队列交替写入、同步、读回同一张 512 × 512 表面，两个插件各 **480/480** 次像素校验通过。这项测试没有显示稳定的速度差异。

## 验证范围与源码

以官方 v3.0 为基线，源码净变化覆盖 **70 个文件**，其中 33 个在测试目录。核对的 20 个二进制组件中，6 个发生变化：两个系统版本的 NVAccel、NVRMFB、NVMTLDriver、NVK 和 VideoToolbox 库。安装器面向上表中的 macOS 26 环境。适用于本机的 19 个组件均与已安装文件逐字节一致。

外层 PKG 未使用 Developer ID Installer 签名，Metal 插件采用本机实测的诊断构建。已做包内文件、哈希和安装选项校验；整合封装本身尚未单独完成覆盖安装、重启和回退验证。源码快照的宿主测试为 **256 项通过、8 项失败、10 项未运行**，逐项结果在 `evidence/host-tests/`。NVRM/NVK 单次 fence 跟踪及 NVK Boost 续期实验仅随源码归档，其中 Boost 实验仍有测试失败。

安装包实际随附 Khronos Vulkan Loader 1.4.362（`libvulkan.1.4.362.dylib`）。源码归档中的上游 `NOTICE` 保留其 1.4.367 构建说明。
